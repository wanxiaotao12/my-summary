# 概念与指令（编写 Dockerfile）

> 这是三篇 Dockerfile 文档的第一篇，聚焦「怎么写」。写好之后的构建与运行见 [02-构建与运行.md](./02-构建与运行.md)，实战模板、优化技巧与常见问题见 [03-最佳实践.md](./03-最佳实践.md)。

## 什么是 Dockerfile

Dockerfile 是一个纯文本文件，通过一系列指令定义如何构建 Docker 镜像。它是镜像的"配方"，任何人使用同一个 Dockerfile 都能构建出完全一致的镜像。

### 为什么需要 Dockerfile

核心目的是**构建镜像**——把"如何把应用打包成镜像"这件事用文件固化下来。在此基础上还带来三个好处：

- **环境一致性**：应用跑不起来，往往不是代码问题，而是环境差异——依赖缺了、系统库版本不对、路径不一样。Dockerfile 把"装什么依赖、配什么环境"写成代码，消除了手工搭环境的不确定性。开发、测试、生产用同一个构建配方，应用的运行环境就是一致的，不再需要挨个机器排查环境差异。
- **版本控制**：用 Git 管理镜像配置，追踪变更历史
- **自动化**：CI/CD 流水线中自动构建，无需人工干预

> **注意**："一致"不是指镜像文件逐字节相同。以下几种情况下，同一个 Dockerfile 在不同时间或机器上构建出的镜像会有差异：基础镜像标签未锁定具体版本（如 `python:3.9-slim` 会随时间更新）、`RUN apt-get install` 拉的是仓库最新版、跨 CPU 架构（ARM vs x86）构建产物的指令集不同。要追求精确一致，需要指定基础镜像摘要（digest）、锁定包版本、指定构建平台。

### 工作流中的位置

从编写到应用跑起来分为三步，Dockerfile 是第一步：

```
第一步              第二步            第三步
编写 Dockerfile  ──▶  构建镜像  ──▶  运行容器
（构建配方）         （可分发的产物）   （运行中的实例）
```

- **编写**——定义基础镜像、要复制的文件、要执行的命令
- **构建**——`docker build` 逐条执行指令，生成可分发、可版本化的镜像
- **运行**——`docker run` 基于镜像启动容器，应用真正跑起来

### 文件约定

Dockerfile 是**可选的**——只有需要自定义镜像时才写它。如果只是为了跑数据库、缓存等现成服务，直接用 `docker run mysql:8.0` 就行，不需要任何 Dockerfile。

如果决定写一个，遵循以下约定：

| 属性 | 说明 |
|------|------|
| 文件名 | 习惯上用 `Dockerfile`（无扩展名，首字母大写）。也可用其他名字，没有格式要求，构建时用 `-f` 指定即可（如 `Dockerfile.prod`、`Dockerfile.dev`） |
| 文件格式 | 纯文本，每行一条指令 |
| 编码 | UTF-8 |

### 存放位置

推荐放在**项目根目录**，文件名固定为 `Dockerfile`：

```
my-project/
├── Dockerfile
├── .dockerignore
├── app.py
├── requirements.txt
└── README.md
```

原因：`docker build` 默认在当前目录找 `Dockerfile`，COPY 指令的路径也相对于此。

也可自定义文件名和位置——构建时用 `-f` 指定（详见 [02-构建与运行.md](./02-构建与运行.md)）。

## 运行机制：docker build 做了什么

执行 `docker build` 时，Docker 逐条读取 Dockerfile 中的指令，每一条指令生成一个**镜像层（layer）**。最终镜像就是这些层按顺序叠在一起的只读文件系统。

一个简单的 Dockerfile：

```dockerfile
FROM python:3.9-slim          # 层1：基础镜像
WORKDIR /app                   # 层2：创建工作目录
COPY requirements.txt .        # 层3：复制依赖文件
RUN pip install -r requirements.txt  # 层4：安装依赖
COPY . .                       # 层5：复制源代码
CMD ["python", "app.py"]       # 层6：记录启动命令（不产生文件变更）
```

构建过程中，上面每条指令产生的层依次叠加，最终镜像就是这 6 层的合集。

### 层的三个特性

**1. 只读叠加**：每一层是上一层基础上的"增量变更"——COPY 添加了文件、RUN 安装了包。下层文件可以被上层"覆盖"（实际是遮蔽），但无法修改或删除下层的文件。最终容器看到的是所有层的合并视图。

**2. 缓存复用**：每次构建时，Docker 会检查每一条指令的输入是否跟上次一样。如果 FROM 的基础镜像没变、COPY 的文件内容没变、RUN 的命令文本没变，Docker 直接复用上次的缓存层，跳过执行。这就是"为什么 `COPY requirements.txt` 放在 `COPY . .` 前面"的原因——只有依赖文件变更时才重装依赖，改一行源代码不会触发重新 pip install。

**3. 层越多镜像越大**：每条 RUN、COPY、ENV、WORKDIR 都会产生一个新层。所以 RUN 指令推荐用 `&&` 合并——三行独立 RUN 就是三层，一行合并就是一层的"增量"。

### 一个具体的构建过程

```
docker build -t my-app:v1.0 .

Step 1/6 : FROM python:3.9-slim          → pull 基础镜像（或复用缓存）
Step 2/6 : WORKDIR /app                   → 在层上创建 /app 目录
Step 3/6 : COPY requirements.txt .        → 将本地文件写入层
Step 4/6 : RUN pip install -r ...         → 在层上执行命令，产生新文件
Step 5/6 : COPY . .                       → 将源代码写入层
Step 6/6 : CMD ["python", "app.py"]       → 在镜像元数据中记录启动命令

Successfully tagged my-app:v1.0
```

### 与容器的关系

镜像层是只读的。运行容器时，Docker 在所有镜像层之上再叠加一个**可写层（container layer）**——容器运行时的所有文件修改都发生在这个可写层上。删除容器，可写层也随之删除，镜像层不变。这就是为什么容器可以秒级销毁重建，而数据要持久化必须用数据卷。

## 指令速览

按在 Dockerfile 中的典型出现顺序排列：

| 指令 | 一句话作用 |
|------|-----------|
| `FROM` | 指定基于哪个基础镜像构建 |
| `WORKDIR` | 设置后续指令的工作目录 |
| `RUN` | 构建镜像时执行 Linux 命令 |
| `COPY` | 将本地文件复制到镜像 |
| `ENV` | 设置环境变量 |
| `EXPOSE` | 声明容器监听的端口 |
| `CMD` | 容器启动时的默认命令 |
| `ENTRYPOINT` | 容器启动时的固定入口命令 |
| `ARG` | 定义构建时变量 |
| `VOLUME` | 声明数据卷挂载点 |
| `USER` | 指定容器运行的用户 |

> 注意：几乎每条指令都会生成一层镜像层（RUN、COPY、ENV、WORKDIR 等），层数越多镜像体积越大。

## FROM — 指定基础镜像

每个 Dockerfile 必须以 FROM 开头。

### 命令格式

```
FROM [仓库名/]镜像名[:标签]
```

| 组成部分 | 说明 | 示例 |
|----------|------|------|
| 仓库名（可选） | 不填默认 Docker Hub | `node` |
| 镜像名 | 镜像名称 | `python`、`node`、`openjdk` |
| 标签（可选） | 版本标签，不填默认 `latest` | `3.9-slim`、`18-alpine` |

### 命令示例

```dockerfile
FROM python:3.9-slim
```

### 示例解析

| 完整写法 | 仓库 | 镜像 | 标签 |
|--------|------|------|------|
| `python:3.9-slim` | Docker Hub | python | 3.9-slim |
| `node:18-alpine` | Docker Hub | node | 18-alpine |
| `openjdk:17-slim` | Docker Hub | openjdk | 17-slim |
| `myregistry.com/myapp:v1.0` | myregistry.com | myapp | v1.0 |

**常用基础镜像**：

| 基础镜像 | 适用场景 |
|----------|----------|
| `python:3.9-slim` | Python 应用，体积较小 |
| `node:18-alpine` | Node.js 应用，体积极小 |
| `openjdk:17-slim` | Java 应用 |
| `golang:1.21` | Go 编译环境 |
| `scratch` | 空镜像，用于编译后的静态二进制 |

## WORKDIR — 设置工作目录

设置后续指令的工作目录。目录不存在则自动创建。

### 命令格式

```
WORKDIR [目录路径]
```

| 组成部分 | 说明 | 示例 |
|----------|------|------|
| 目录路径 | 镜像中的绝对路径 | `/app` |

### 命令示例

```dockerfile
WORKDIR /app
```

### 作用说明

- **位置**：通常放在 FROM 之后、RUN/COPY 之前
- **默认值**：未设置时为根目录 `/`
- **影响范围**：既影响构建时（RUN、COPY 等），也影响运行时（`docker exec` 进入时的默认目录）

设置 WORKDIR 后，COPY 和 RUN 中的 `.` 都指向该目录：

```dockerfile
WORKDIR /app
COPY . .
RUN pip install .
```

等价于：

```dockerfile
COPY . /app
RUN cd /app && pip install .
```

## RUN — 执行命令

在构建时执行 Linux 命令。

### 命令格式

```
RUN [命令]
```

### 命令示例

```dockerfile
RUN pip install -r requirements.txt
RUN apt-get update && apt-get install -y curl
```

### 最佳实践

用 `&&` 合并多条命令，减少镜像层数：

```dockerfile
# 推荐：合并为一层
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

# 不推荐：生成三层
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
```

## COPY — 复制文件到镜像

将文件复制到镜像中。

### 命令格式

```
COPY [--from=<阶段名>] [源路径] [目标路径]
```

| 组成部分 | 说明 | 示例 |
|----------|------|------|
| `--from`（可选） | 从其他构建阶段复制（多阶段构建用） | `--from=build` |
| 源路径 | 相对路径（相对于 Dockerfile 所在目录）或绝对路径 | `requirements.txt`、`src/`、`.` |
| 目标路径 | 镜像中的路径 | `.`（当前 WORKDIR）、`/app/` |

**目录复制示例**：假设结构如下：

```
my-project/
├── Dockerfile
├── src/
│   ├── main.py
│   └── utils/
│       └── helper.py
```

`COPY src /app/src` → 镜像中：

```
/app/src/
├── main.py
└── utils/
    └── helper.py
```

子目录和文件会一并递归复制。

### 命令示例

```dockerfile
COPY requirements.txt .
COPY . .
```

| 命令 | 含义 |
|------|------|
| `COPY requirements.txt .` | 将 requirements.txt 复制到镜像工作目录 |
| `COPY . .` | 将 Dockerfile 所在目录下所有文件（受 .dockerignore 排除）复制到工作目录 |
| `COPY src /app/src` | 将 src 目录复制到 /app/src |

### COPY 与 ADD 的区别

| 指令 | 区别 |
|------|------|
| `COPY` | 仅复制文件/目录 |
| `ADD` | 额外支持 URL 下载和自动解压 tar |

**优先使用 COPY**，行为更明确。

### 从其他构建阶段复制（`--from`）

多阶段构建的核心写法：

```dockerfile
COPY --from=build /build/target/app.jar .
```

| 写法 | 复制来源 |
|------|----------|
| `COPY app.jar .` | 从本地电脑（构建上下文） |
| `COPY --from=build /build/target/app.jar .` | 从另一个构建阶段 |

详见 [03-最佳实践.md](./03-最佳实践.md) 的「多阶段构建」。

## ENV — 设置环境变量

设置的是**默认值**，运行时可用 `-e` 覆盖：

```bash
docker run -e APP_PORT=9000 my-app   # 覆盖，镜像不变
```

### 命令格式

```
ENV [变量名]=[变量值]
```

### 命令示例

```dockerfile
ENV PYTHONUNBUFFERED=1
ENV APP_PORT=8000
```

| 命令 | 含义 |
|------|------|
| `ENV PYTHONUNBUFFERED=1` | Python 输出不缓冲，日志实时打印 |
| `ENV APP_PORT=8000` | 应用端口默认 8000 |

设置后代码中可通过 `os.environ.get("APP_PORT")` 读取。

## EXPOSE — 声明端口

**只是"备注"**，并不真正开通端口。两个实际用处：

- **文档作用**：`docker inspect` 时能看到设计端口，不用翻代码
- **配合 `-P`**：`docker run -P` 自动将声明的端口随机映射到宿主机

### 命令格式

```
EXPOSE [端口号]
```

### 命令示例

```dockerfile
EXPOSE 8000
```

### EXPOSE 与 -p 的区别

| 写法 | 作用 |
|------|------|
| `EXPOSE 8000`（Dockerfile 里） | 只是备注 |
| `docker run -p 8000:8000`（运行时） | **真正**映射端口 |

## CMD — 容器启动命令

容器启动时的**默认**命令——运行时不指定就用它，指定了就让位。

### 命令格式

```
CMD ["命令", "参数1", "参数2"]
```

### 命令示例

```dockerfile
CMD ["python", "app.py"]
```

### 两种覆盖

**构建时**：多条 CMD 只有最后一条生效（一个容器只该有一个主进程）：

```dockerfile
CMD ["python", "app.py"]
CMD ["python", "server.py"]     # 只有这条被保留
```

**运行时**：`docker run` 指定命令时 CMD 让位：

```bash
docker run my-image              # 用 CMD
docker run my-image bash         # CMD 被顶掉，改跑 bash
```

## ENTRYPOINT — 容器入口点

与 CMD 类似，但**不可被 `docker run` 覆盖**。CMD 的参数会成为 ENTRYPOINT 的附加参数。

### 命令格式

```
ENTRYPOINT ["命令", "参数1", "参数2"]
```

### 命令示例

```dockerfile
ENTRYPOINT ["python", "app.py"]
```

### CMD 与 ENTRYPOINT 的选择

| 场景 | 使用 |
|------|------|
| 固定命令，参数可变 | ENTRYPOINT + CMD（CMD 提供默认参数） |
| 默认命令，可被覆盖 | CMD |

## ARG — 构建时变量

只在 `docker build` 时存在，运行时不存在。

### 命令格式

```
ARG 变量名[=默认值]
```

### 命令示例

```dockerfile
ARG VERSION=1.0
RUN echo "building version ${VERSION}"
```

构建时传参：

```bash
docker build --build-arg VERSION=2.0 -t my-app .
```

### ARG 与 ENV 的区别

| 指令 | 生效时机 | 运行时存在 |
|------|----------|-----------|
| `ARG` | 仅构建时 | 否 |
| `ENV` | 构建时 + 运行时 | 是 |

常见组合：

```dockerfile
ARG VERSION=1.0
ENV APP_VERSION=${VERSION}
```

## VOLUME — 声明数据卷

声明容器内目录为数据卷，用于数据持久化。

**不是必须的**——它只是在镜像元数据里打"建议标记"；真正决定数据存哪里的是 `docker run -v`，且 `-v` 不依赖 VOLUME。实际生产中很多团队不写 VOLUME，直接在部署时 `-v` 挂载。

### 命令格式

```
VOLUME [目录路径]
```

### 命令示例

```dockerfile
VOLUME /data
```

**运行时挂载**（这一步才真正持久化）：

```bash
docker run -v /host/data:/data my-app
# 左边：宿主机目录   右边：容器目录
```

## USER — 指定运行用户

容器默认以 **root** 运行，生产环境应切换到低权限用户。

### 命令格式

```
USER 用户名[:用户组]
```

### 命令示例

```dockerfile
RUN useradd -m appuser
USER appuser
```

> USER 指定的用户必须先存在，所以通常先用 `RUN useradd` 创建。

## 多阶段构建

### 概念

一个 Dockerfile 可写**多个 FROM**，每个 FROM 开启一个独立的构建阶段。Docker 按顺序执行所有阶段，但最终镜像只保留最后一个阶段的内容。核心写法：`FROM ... AS <阶段名>` + `COPY --from=<阶段名>`。

### 为什么需要

以 Java 项目为例，从源码到可运行，需要先编译（`mvn package`）。有两种做法：

**方案 A：本地编译好，Dockerfile 只负责运行**
```
本机 → mvn package → 拿到 app.jar → Dockerfile 里 COPY app.jar → 构建镜像
```
好处是 Dockerfile 简单，镜像也小。但**跟 Docker 的初衷矛盾**——你本机得装 Maven、要确保 JDK 版本对，换一台机器、换一个同事、上 CI 流水线，都要重新保证编译环境一致。Dockerfile 只描述了"怎么跑"，没描述"怎么从源码到产物"，构建过程没有容器化。

**方案 B：多阶段构建**
```
Dockerfile 里：
  阶段1（maven 镜像）→ 编译出 app.jar
  阶段2（jdk slim 镜像）→ COPY --from=阶段1 app.jar → 最终镜像只含运行环境
```
编译也在 Dockerfile 里完成。**任何装了 Docker 的机器**——不管本机有没有 Maven、JDK 什么版本——都能从源码一步构建出最终镜像。构建过程完全容器化，端到端一致。

多阶段构建的本质不是"省体积"（虽然最终镜像确实更小），而是**把编译也纳入 Dockerfile，让从源码到镜像的全流程在所有机器上都一致**。

### 结构模板

```text
FROM <编译镜像> AS <阶段名>
... 编译指令（COPY 源码、RUN 编译）

FROM <运行镜像>
... 运行指令
COPY --from=<阶段名> <产物> <目标路径>
CMD [...]
```

| 写法 | 说明 |
|------|------|
| `FROM <镜像> AS <阶段名>` | 开启一个阶段并起别名（如 `AS build`），供后续阶段引用 |
| `COPY --from=<阶段名> ...` | 从指定阶段复制文件，而非从本地电脑复制 |

具体示例见 [03-最佳实践.md](./03-最佳实践.md) 的「语言实战模板」中 Java 应用的多阶段构建。
